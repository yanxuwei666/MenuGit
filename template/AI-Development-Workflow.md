# MenuGit AI 辅助开发流程

## 目的

本文件规定 MenuGit 从产品需求、竞品研究和原型，到技术方案、AI 实现、验收与迭代的协作方式。目标是让每项实现都有明确依据和验收标准，减少 AI 对需求的猜测、跨模块扩散和重复返工。

产品功能与交互以经确认的 PRD 和原型为准。本流程文档约束开发过程，不替代产品决策。技术方案在需求和原型经过确认后单独形成；若后续验证推翻了早期假设，应回到对应阶段更新，而不是把错误假设继续写进代码。

编写项目需求时可使用 [通用项目需求说明书模板](通用项目需求说明书模板.md)，按项目范围裁剪并记录不适用项。

## 协作原则

1. **先明确用户问题，再确定功能。** 从目标用户、使用场景和现有解决办法出发，不以功能清单作为需求起点。
2. **原型用于验证行为。** 页面外观、主要操作路径、状态变化和用户反馈应与计划实现一致；底层 Git 操作可以先使用模拟数据。
3. **首版范围明确。** 每项需求标记为首版、后续版本或明确不做，并说明优先级依据。
4. **AI 在已确认的边界内执行。** AI 可以发现问题并提出方案；会改变已确认的产品行为、架构边界或首版范围的决定，需要先作为决策项提出。
5. **按完整用户流程切片。** 每个开发任务覆盖一个可独立理解、实现和验收的流程，避免一次任务横跨整个产品。
6. **结论保留依据。** 重要需求、取舍、技术决策和验收结果写入对应文档，避免依赖聊天记录。
7. **逐个平台验证。** 共享的产品行为尽量一致；操作系统集成、权限、安装和发布差异分别列出并验收。

## 阶段与交付物

### 阶段 0：产品目标与约束

先回答以下问题：

- 谁会使用 MenuGit？
- 他们当前在哪个场景遇到什么问题？
- 现在如何解决，为什么现有办法不够好？
- 产品希望带来什么可观察的改善？
- 有哪些平台、资源、安全或时间约束？

**交付物：** 一页产品机会说明，包括目标用户、主要场景、核心问题、产品目标、约束和暂不处理的范围。

**检查点：** 核心问题和目标用户足够具体，可以据此判断某项功能是否有价值。

### 阶段 1：需求与同类产品研究

围绕目标用户的任务研究直接竞品、间接替代品和用户当前采用的办法。比较它们的核心工作流程、学习成本、平台支持和明显限制，重点寻找未被满足的用户需要。

把差异化表达为可以验证的假设，例如“第一次使用 Git 的用户能独立完成常见操作”，而不是只写抽象的产品口号。将需求整理成功能模块，并标注优先级和依据。

**交付物：** 研究摘要、需求清单、模块图、差异化假设，以及首版/后续/不做的范围划分。

**检查点：** 首版范围直接服务于已确认的用户问题；每项高优先级需求都有场景和价值依据。

### 阶段 2：需求规格与验收标准

把每个首版需求写成用户场景和可观察结果。关键操作需要定义成功、失败、加载、空结果、取消和权限不足等状态。破坏性操作要明确确认方式、影响范围和撤销可能性。

需求应能被验证，避免“好用”“简洁”“像原型”这类无法直接判断的描述。具体文案、按钮状态和数据变化尽量落到页面或流程级别。

**交付物：** PRD、首版需求列表、用户流程和逐项验收标准。

**检查点：** 产品负责人和实现者对需求完成后的表现有共同理解。

### 阶段 3：原型与交互验证

先整理信息架构和核心用户流程，再制作原型。原型应覆盖首版核心流程及关键异常状态，达到可以让目标用户实际操作并给出反馈的程度。

原型需要在用户层面尽量贴近最终功能：操作顺序、页面状态、反馈和取消行为与计划实现一致。可以模拟 Git 仓库和命令结果；涉及真实 Git、系统菜单、权限、凭据和平台交接的技术可行性，单独在技术阶段验证。

原型工具按验证目标选择。视觉探索、点击流程测试和接近真实运行行为是不同任务，不要求一种工具同时完成全部验证。HTML 原型可以继续使用；如果迭代视觉和组织页面状态不方便，可以改用设计工具制作流程原型，或针对高风险交互做小型可运行验证。

按具体任务进行原型走查：让使用者尝试完成操作，记录卡点、误解和遗漏状态，再修订原型。通过标准不是页面都能点击，而是用户能理解下一步、理解结果，并在异常情况下知道如何处理。

**交付物：** 页面清单、用户流程图、状态与交互说明、可操作原型、走查问题及其处理结果。

**检查点：** 首版核心流程已经走查；影响理解或操作结果的问题已解决或明确记录。

### 阶段 4：技术方案与风险验证

基于已确认的需求和原型制定技术方案。至少明确：

- 技术栈和模块职责；
- 前端、Git 能力、桌面壳和各平台系统集成之间的边界；
- 前后端接口、错误类型和数据模型；
- 数据、凭据、权限和破坏性操作的处理方式；
- 构建、发布、平台适配和验收方式。

先识别高风险假设。若某项平台能力、Git 行为、安全约束或依赖选择可能改变方案，先做范围受限的技术验证，再锁定架构。验证只回答特定问题，不借机扩展成另一套产品实现。

**交付物：** 技术方案、模块/API 契约、风险清单、技术验证结论和首版开发顺序。

**检查点：** 首版需求能够映射到实现模块；关键风险已有证据或明确的后续验证计划。

### 阶段 5：开发计划与任务拆分

将首版范围按用户价值、依赖关系和风险排序，拆成垂直切片。一个切片通常从界面操作贯通到真实结果和反馈；基础设施任务只有在确实支撑这些流程时才单独安排。

每项任务应有唯一目标、前置条件、允许修改的模块、验收条件和非目标。跨平台工作需标明适用平台，以及共享部分和平台专属部分。

**交付物：** 有序里程碑、任务清单、依赖关系和每项任务的验收条件。

**检查点：** 每项任务都能独立交付并判断完成，任务顺序不会要求实现者猜测未定的产品行为。

### 阶段 6：AI 辅助实现

每轮开发按以下顺序进行：

1. 给 AI 提供本任务相关的 PRD、原型、技术方案和当前代码上下文。
2. 要求 AI 概括理解、列出将修改的模块和可能的冲突点。
3. 在已确认的任务范围内实现；遇到会改变产品行为或架构的决定时，先提出选项和影响。
4. 检查差异，确认没有无关重构、遗漏状态或偏离原型的行为。
5. 按任务验收条件检查结果，通过后记录完成情况并保存代码检查点。

**交付物：** 一个范围清楚的代码变更、验收记录、已知问题和更新后的进度。

**检查点：** 变更与需求、原型和技术方案一致；实现者能说明每项改动的目的及验证结果。

### 阶段 7：版本验收与迭代

按 PRD 的验收标准完成首版验收，并分别验证共享流程和各平台专属行为。发现的问题记录为缺陷、需求调整或后续优化，避免把未确认的临时改动直接带入下一轮。

发布后收集真实使用反馈，重新评估需求假设、优先级和平台安排。重大变化回到需求、原型或技术方案阶段更新文档和验收标准。

**交付物：** 版本验收记录、已知限制、反馈汇总和下一版本排序后的计划。

## 单项 AI 开发任务模板

```text
任务目标：用户要完成什么，以及本任务要交付的结果。

用户场景：用户从什么状态开始，执行什么操作，预期看到什么结果。

需求与原型依据：PRD 章节、页面/流程、对应的状态与交互说明。

技术约束：必须遵守的模块边界、API 契约、平台限制和安全要求。

验收条件：逐条列出正常、失败、取消及相关边界状态的可观察结果。

修改范围：本任务允许修改的页面、模块或接口。

非目标：本任务明确不做的功能、平台和重构。

完成后汇报：变更摘要、验收方式与结果、未完成事项、需要产品决策的问题。
```

## 变更与决策记录

- 用户需求变化时，先更新需求及验收标准，再调整原型和任务计划。
- 原型变更影响已确认行为时，同步更新需求说明。
- 技术方案变更影响产品行为、平台范围、安全或发布计划时，记录原因、影响和替代方案。
- 每轮结束更新里程碑和未解决事项；保留重要取舍及其依据。
- 不以聊天记录作为唯一的需求或决策存档。

## 完成定义

单项开发任务只有在功能符合已确认的需求和原型、验收条件通过、平台适用范围明确、遗留问题已记录后才算完成。一个版本只有在首版范围逐项验收、平台差异已检查、发布方式和已知限制清楚后才算可交付。
